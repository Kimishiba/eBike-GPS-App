# Research: BLE proximity auto-connect

Resolves [eBike-GPS-App#10](https://github.com/Kimishiba/eBike-GPS-App/issues/10). Investigates whether/how the companion app can auto-connect to a paired Board over BLE when the phone comes near the bike, given the firmware direction already proposed in `eBike-GPS-Tracker` PR #30, and given OS-level background-BLE constraints on iOS and Android. The "Client platform choice" ticket (issue #6) is still open, so this covers native iOS/Android plus where a cross-platform framework (React Native, Flutter) would ride the same OS limits vs. need a plugin/bridge.

## 1. Firmware side (PR #30)

[`Kimishiba/eBike-GPS-Tracker` PR #30, "BLE proximity auto-disarm design (Android)"](https://github.com/Kimishiba/eBike-GPS-Tracker/pull/30) is a design-doc-only PR (`ble-proximity-design.md`, no code), currently **open**. It answers a narrower question than "auto-connect when the phone is near the bike" — its stated goal is "the bike silences its own alarm when the owner walks up to it, without them taking their phone out" — but the wire protocol and BLE role split it settles are exactly the fixed constraints the app has to build against.

Key conclusions the app side should treat as given:

- **Trigger is motion, not ambient proximity.** The ESP32 fully powers down its radio in deep sleep and cannot advertise while asleep (unlike an nRF52), so continuous "bike notices phone approaching while parked" is off the table with current hardware. The board only starts advertising after the ADXL345 activity-interrupt wake (merged in tracker #17) — i.e., when someone physically touches/moves the bike. This means the app cannot rely on a bike that's always advertising; it has to be ready to react to bursty ~8-second advertising windows that start unpredictably.
- **Bike is the BLE peripheral, phone is the central.** Rejected the reverse (bike scanning for a known phone address) because both platforms randomize BLE addresses (Android roughly every 15 min) and because presence broadcast in the clear isn't authentication. This confirms the app's role: it scans/connects, it does not advertise.
- **One fleet-wide 128-bit GATT service UUID**, static, so a scan filter can be UUID-based rather than per-device. Three characteristics: `CHALLENGE` (read/notify, 16-byte nonce), `RESPONSE` (write, 32-byte HMAC-SHA256), `STATUS` (read/notify, armed state + result code). Challenge–response auth, no BLE bonding (no LESC pairing) — the key (`ble_key = HKDF(device_secret, "ble-proximity-v1")`) is provisioned to the app once over TLS at claim time and stored in the Android Keystore.
- **Grace window ~8s**, worst case, from advertising start to disarm decision (2–6s Android background scan detection via `SCAN_MODE_LOW_POWER` duty cycle + 0.5–2s GATT connect + 0.1–0.3s challenge round trip). This is the latency budget the app-side scan/connect path needs to fit inside if it wants to catch the window while it's open.
- **Explicitly scoped to Android only.** iOS is excluded in the doc's §9 with reasons recorded so it isn't relitigated for *this specific proposal*: in the phone-as-peripheral direction (irrelevant here, but the doc considered it) iOS backgrounds custom service UUIDs into an OS-only "overflow" area invisible to non-Apple scanners. For the direction actually chosen (bike-as-peripheral), the doc notes the workable iOS route would be the bike advertising an iBeacon frame with the app using `CLLocationManager.startMonitoring(for:)`, requiring "Always" location permission and roughly doubling the app-side work — tractable, just not built into this PR.
- **What's still open / not yet code**: this is a design doc, not merged firmware. It flags an unresolved interaction with `provisioning-design.md` §5 (a relay-attacked BLE disarm could invalidate a factory-reset safety assumption; tracked as tracker issue #37) and a partition-table sizing question for tracker issue #27 (NimBLE adds ~150KB flash). Nothing here is shipped; the app side should not assume the GATT service exists on hardware yet.

**Net for the app:** the firmware, if this design lands as proposed, gives the app a single well-known service UUID to scan for, three characteristics to talk to, and a design assumption that connections are short, bursty, and initiated by the app the moment it sees the bike advertising after motion — not a long-lived always-on link.

## 2. iOS constraints

Primary source: [Apple, "Core Bluetooth Background Processing for iOS Apps"](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html) and related Apple reference pages ([`CBCentralManagerRestoredStatePeripheralsKey`](https://developer.apple.com/documentation/corebluetooth/cbcentralmanagerrestoredstateperipheralskey), [`centralManager(_:willRestoreState:)`](https://developer.apple.com/documentation/corebluetooth/cbcentralmanagerdelegate/centralmanager(_:willrestorestate:))).

- **`bluetooth-central` background mode** (declared in `Info.plist` `UIBackgroundModes`) is required for any background Core Bluetooth central activity. With it declared, the app can discover/connect to peripherals, read/write characteristics, and receive delegate callbacks (connect/disconnect, characteristic updates, state changes) while backgrounded.
- **What wakes the app in the background is a delegate callback, not a beacon-style region entry.** Core Bluetooth central scanning has no built-in "region monitoring" concept — the app is woken by `CBCentralManagerDelegate`/`CBPeripheralDelegate` callbacks for events it was already set up to observe (e.g., matching an active scan filter, or a connection event on a peripheral it already knows about). This is a meaningfully different (weaker) wake guarantee than iOS's CoreLocation beacon region monitoring, covered below.
- **Background scanning is deliberately throttled.** When the scanning app is backgrounded, iOS ignores `CBCentralManagerScanOptionAllowDuplicatesKey` (multiple sightings of the same peripheral coalesce into one event) and increases the scan interval, i.e. slower discovery, explicitly "to minimize radio usage and improve battery life."
- **Background execution time is short.** Once woken, the app gets roughly 10 seconds to act before iOS can suspend it again; Apple's guidance is to do the minimum necessary work and return quickly.
- **State preservation & restoration** (`CBCentralManagerOptionRestoreIdentifierKey`) lets the system keep tracking pending BLE events (matching a scan, a pending connection, subscribed characteristics) even after the app process is fully terminated by the OS, and relaunch the app via `centralManager(_:willRestoreState:)` when something relevant happens, handing back the restored state (peripherals, scan services) via keys like `CBCentralManagerRestoredStatePeripheralsKey`. This is the mechanism that makes "was killed, still gets woken when the bike shows up" possible on iOS — but it depends on the OS's own judgment about when to relaunch, and Apple's docs are explicit the app "can't run forever": it may still be terminated to free memory for the foreground app, with no guaranteed floor on wake reliability.
- **Battery framing**: Apple's own docs frame all of the above (duplicate coalescing, longer scan interval, 10s execution budget) as battery-motivated tradeoffs — the platform is actively trading discovery latency for battery life the moment the app isn't in the foreground. There's no published concrete mAh/hour figure for continuous background scan of a specific service UUID; the qualitative guidance is consistent that raw continuous scanning in the background is discouraged in favor of the leaner delegate/restoration model above.
- **iBeacon / region monitoring alternative** ([`CLBeaconRegion`](https://developer.apple.com/documentation/corelocation/clbeaconregion), `CLLocationManager.startMonitoring(for:)`): this is CoreLocation, not Core Bluetooth, and it is the pattern Apple recommends for "detect proximity to a specific known device" style use cases. It requires "Always" location authorization, but in exchange it can launch a **terminated** app on region entry/exit with a stronger OS-level guarantee than Core Bluetooth's restoration mechanism, because the radio-level beacon detection is handled by the OS/hardware rather than the app's own CBCentralManager scan. This is exactly the route PR #30 §9 names as the workable-but-undone iOS path (bike advertises an iBeacon frame in addition to/instead of a plain GATT service advertisement; app uses region monitoring to wake, then connects via Core Bluetooth for the actual challenge–response GATT exchange).

## 3. Android constraints

Primary sources: [Android Developers, "Communicate in the background" (BLE)](https://developer.android.com/develop/connectivity/bluetooth/ble/background), [Android Developers, "Optimize for Doze and App Standby"](https://developer.android.com/training/monitoring-device-state/doze-standby), [Android Developers, "App Standby Buckets"](https://developer.android.com/topic/performance/appstandby).

- **`BluetoothLeScanner.startScan(filters, settings, PendingIntent)`** (API 26+) is the recommended background pattern: the system holds the scan filter and fires the `PendingIntent` when a matching advertisement is seen, even if the app process isn't currently running — the app doesn't need to hold a wakelock or run a persistent foreground service just to wait. Android's own docs are explicit that **scan filters are required** for this to be efficient, and that periodic unfiltered/scheduled scanning "to find devices is discouraged" because it wakes the app process regardless of whether the target device is actually in range.
- **Foreground service rules changed at API 31 (Android 12).** Below API 31, you could start a foreground service directly from the `PendingIntent` callback. From API 31 on, background-start restrictions on foreground services apply, and Android's guidance shifts to starting a `Worker`/`Job` instead for short-duration work, escalating to a foreground service only under one of the documented background-start exemptions if a longer-lived connection is genuinely needed.
- **`ScanSettings` scan modes trade latency for power.** `SCAN_MODE_LOW_POWER` (the default) scans roughly 0.5s on / 4.5s off — this is the mode PR #30's own latency budget (2–6s detection) is built around. Higher-power modes detect faster at higher battery cost.
- **Doze and App Standby actively rate-limit background work independent of the scan API used.** In Doze, network access is suspended outside periodic maintenance windows, JobScheduler/WorkManager tasks don't run, standard alarms are deferred (only `setExactAndAllowWhileIdle()`-class alarms fire, capped at once per ~9 minutes per app), and Wi-Fi scans are explicitly disabled. App Standby Buckets (API 28+) impose separate caps by usage recency — e.g. an app in the "rare" bucket gets a bounded job-execution budget per rolling 24h window. Android's docs don't call out BLE scanning by name in this list, but a `PendingIntent`-based scan sits outside the JobScheduler/alarm machinery specifically so it isn't subject to the same throttling — the tradeoff is that the *response* to a scan hit (starting work, connecting GATT) can still be deferred or constrained by Doze/Standby if it's routed through a Worker/Job rather than handled immediately in the receiver.
- **`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`** (battery-optimization allowlisting) is the escape hatch for apps whose core function needs reliable background BLE connectivity, and Android's Play policy explicitly lists "peripheral device companion" apps needing a persistent connection to a paired device as an *acceptable* use case for requesting it — this matches the eBike tracker scenario directly. PR #30 independently arrives at the same conclusion for OEM battery managers (Xiaomi/Samsung/Huawei killing background receivers) and recommends requesting this exemption during onboarding.
- **No first-class "region monitoring" abstraction equivalent to iOS CoreLocation beacon monitoring.** Android's closest built-in analogs are `CompanionDeviceManager` (device pairing plus `startObservingDevicePresence()` to keep the app awake while an associated device is in range — limited filtering, no random-MAC support) or building the equivalent yourself on top of `PendingIntent`-based scanning with a static service-UUID filter, which is effectively what PR #30 already designs.

## 4. What this unlocks

Assuming the app implements the Android-side scan/connect pattern above against the GATT service PR #30 proposes (and, later, the iBeacon/region-monitoring equivalent on iOS):

- **Faster local status and arm/disarm, no backend round trip.** Today, "is the bike armed/where is it/disarm it" has to go phone → backend → MQTT → board (or the reverse for status), which costs at minimum a full cellular round trip through the SIM7000G modem and depends on the bike's telemetry/publish cadence. A direct BLE GATT link (`STATUS` read/notify, `RESPONSE` write) gives the app a local answer in the ~3–8s PR #30 already budgets for the disarm handshake — one to two orders of magnitude faster than a cellular MQTT round trip, and it works with the phone's screen off or the app backgrounded (on Android, reliably via `PendingIntent` scan + Worker/foreground-service escalation; on iOS, with the caveats in §2 around wake reliability and the recommended iBeacon-region fallback).
- **A working fallback when cellular/MQTT is unavailable.** The bike's connectivity to the backend depends on cellular coverage and the SIM7000G's modem boot succeeding; BLE proximity gives the owner a path to arm/disarm and read status that doesn't touch the cellular/MQTT path at all — useful in dead zones, during a modem fault, or simply to avoid burning a cellular wake cycle for an interaction that's happening a meter away. This mirrors PR #30's own framing: BLE disarm is a "convenience layer," not a replacement for the NFC/authenticated-app paths, but it's also not dependent on the thing (cellular backend round trip) that auto-connect is trying to avoid.
- **Recommended pattern given the constraints above: scan-filtered wake, not continuous raw scanning, on both platforms.** On Android, use `BluetoothLeScanner.startScan()` with a `ScanFilter` on PR #30's fleet-wide service UUID and a `PendingIntent`, in `SCAN_MODE_LOW_POWER`, re-registered on `BOOT_COMPLETED`/Bluetooth-toggle as PR #30 already specifies, plus the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` exemption at onboarding. On iOS, the raw Core Bluetooth `bluetooth-central` + state-restoration path works but has a weaker/soft wake guarantee once the app is fully terminated; official guidance points toward layering CoreLocation `CLBeaconRegion` monitoring on top (bike also advertises an iBeacon frame) to get a hard terminated-app wake on region entry, then handing off to Core Bluetooth for the actual GATT challenge–response — exactly the route PR #30 §9 names as the not-yet-built iOS path. Either way, this is a background-BLE-scanning capability the app needs regardless of which framework builds it.
- **Cross-platform framework note (issue #6 still open):** none of the constraints above are framework artifacts — they're OS-level (Core Bluetooth background modes/state restoration on iOS, `BluetoothLeScanner`/Doze/Standby on Android). A React Native or Flutter app would hit the identical limits and would need a native module/plugin bridging to Core Bluetooth and `BluetoothLeScanner` respectively (e.g. `react-native-ble-plx`, `flutter_blue_plus`, or a custom bridge) to get `PendingIntent`-based background scan registration on Android and state-restoration-configured `CBCentralManager` on iOS — off-the-shelf cross-platform BLE plugins vary in how completely they expose these background-specific APIs (background `PendingIntent` scans and state restoration in particular are easy to leave unsupported in a lowest-common-denominator plugin), so this is a concrete area to vet before committing to a cross-platform stack for this feature specifically.
